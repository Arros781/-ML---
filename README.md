Bank Marketing — Churn/Subscription Prediction Service

Бизнес-проблема:
Банк проводит телефонные кампании по продаже срочных депозитов.
Операторы обзванивают клиентов, но соглашающихся всего 12%.
Звонить всем в лоб дорого, потому что большинство звонков
заканчиваются отказом, а бюджет на операторов ограничен.

Задача модели: 
ранжировать клиентов по вероятности подписки,
чтобы звонки шли в первую очередь самым перспективным.
Это снижает стоимость привлечения (cost per acquisition) при том же
бюджете на кампанию.

Звонок клиенту -- 3$ время операторы + минуты связи
Ценность успеха -- 100$ (допущение, фиксируется явно)
Упущенная выгода при пропуске перспективного клиента -- 100$

Отсюда: FN дороже FP примерно в 30 раз -- модель должна быть
агрессивной (низкий порог), а метрика -- cost-sensitive.

Данные 
- Источник: Kaggle adityamhaske/bank-marketing-dataset (оригинал UCI)
- Размер: (45211, 17)
- Таргет: deposit ∈ {yes, no}, доли <no     0.883015 yes    0.116985>
- Лицензия: CC BY 4.0 (UCI)

Метрика

Дисбаланс: 88.3% / 11.7% (1:7.5). Accuracy бесполезна
(«всегда no» = 88.3%).

Две метрики с разными ролями:

1. PR-AUC — главная ML-метрика для сравнения моделей.
   Порого-независима, устойчива к дисбалансу, фокусируется на
   положительном классе.

2. Ожидаемая прибыль кампании (Expected Profit) — главная
   бизнес-метрика для выбора порога:
   profit(t) = Σ 1(p_i > t) · (y_i · margin − cost_call)
   где margin = $100, cost_call = $3 (допущения, фиксируются явно).

Почему не F1: F1 неявно считает FP и FN равноважными, а у нас
FN (упущенный клиент) дороже FP (лишний звонок) ~в 30 раз.

Почему не ROC-AUC как главная: оптимистичен при дисбалансе 1:7.5;
используется как secondary для сравнения моделей.

Порог: выбирается на validation как argmax Expected Profit,
а не 0.5.

Leakage suspects

**`duration` — утечка (target leakage). Выкидываем.**

Длительность текущего звонка известна только после его завершения,
а решение «звонить» принимается до звонка. Признак является
следствием разговора, а не его причиной.

Количественное подтверждение (EDA):

 no (n=39 922) | yes (n=5 289) | Отношение |
| mean duration, сек | 221 | 537 | 2.4× |
| median duration, сек | 164 | 426 | 2.6× |
| 25th percentile | 95 | 244 | 2.6× |
| 75th percentile | 279 | 725 | 2.6× |

Распределения почти не пересекаются: 25-й перцентиль `yes` (244 сек)
выше 75-го перцентиля `no` (279 сек) — модель выучила бы «долгий
звонок → подписка», что бесполезно в проде.

Подтверждение из документации UCI (первоисточник датасета):
- «this attribute highly affects the output target (e.g., if duration=0
- then y='no'). Yet, the duration is not known before a call is performed…
- this input should only be included for benchmark purposes and should be
- discarded if the intention is to have a realistic predictive model.»

`pdays`, `previous`, `poutcome` — НЕ утечка, но требуют обработки.
Это исторические данные о прошлых кампаниях, доступные до звонка.
`pdays = -1` означает «не контактировали» — отдельная категория,
а не число; нельзя оставлять как -1 в числовом признаке без флага.

`day`, `month` — серая зона (temporal).
Это дата последнего контакта в текущей кампании. Для честной
валидации нужен time-based split (см. раздел «Валидация»),
а не случайный KFold.
